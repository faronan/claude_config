# Subagent 起動契約

empirical-prompt-tuning における「両面評価」の入力契約。
実行者（subagent）に渡すプロンプトはこの構造を取る。

## テンプレート

```
あなたは <対象プロンプト名> を白紙で読む実行者です。

## 対象プロンプト
<対象プロンプトの本文を全文貼る or Read で読ませるパスを指定>

## シナリオ
<シナリオの状況設定 1 段落>

## 要件チェックリスト（成果物が満たすべき項目）
1. [critical] <最低ラインに含む項目>
2. <通常項目>
3. <通常項目>
...

判定規則:
- ○ / × / 部分的 の 3 値で各項目を評価
- 部分的の場合は 1 行で理由を添える
- [critical] が全て ○ のときのみ全体成功

## タスク
1. 対象プロンプトに従ってシナリオを実行し、成果物を生成する
2. 終了時に下記レポート構造で返答する

## レポート構造
- **成果物**: <生成物 or 実行結果サマリ>
- **要件達成**: 各項目について ○ / × / 部分的（理由付き）
- **Trace**: 各フェーズに OK / stuck / skipped タグを付ける
  - Understanding（指示を読み、メンタルモデルを組み立てる）
  - Planning（アプローチ・順序を決める）
  - Execution（実際に作業する）
  - Formatting（成果物を期待される形に整える）
  - 折り畳み形式可: 全 OK のときは `Trace: all OK` の 1 行で十分
  - stuck / skipped が 1 つでもあれば phase-by-phase で出す
- **不明瞭点（構造化）**: 各項目について 3 行
  - Issue: <観測された現象>
  - Cause: <指示レベルで診断した原因>
  - General Fix Rule: <その場限りではなく、このクラスの誤りを防ぐクラスレベルのルール>
- **裁量補完**: 指示で決まっておらず自分の判断で埋めた箇所（箇条書き）
- **再試行**: 同じ判断をやり直した回数とその理由
```

## 呼び出し側の処理

- レポートから自己申告部分を抽出
- `tool_uses` / `duration_ms` を Agent ツールの usage メタから取得
- 評価軸表に値を埋める
- `[critical]` 失敗時は「どの critical が落ちたか」を提示フォーマットの不明瞭点節に 1 行添える

## 構造審査モード（補助）

empirical 評価ではなくテキスト整合性チェックだけ行いたい場合は、上記テンプレ冒頭に次を挿入:

```
## モード
構造審査モード: 実行ではなくテキスト整合性チェック。
- description ↔ body の整合
- セクション参照の死リンク
- allowed-tools と Workflow の不整合
- 用語のブレ
を観点に静的レビューする。
```

これにより subagent は環境制約節の skip 動作に引っかからず、静的レビューを返せる。
構造審査は empirical の代替ではなく補助（連続クリア判定には使えない）。

## 並列 dispatch

複数シナリオを同時実行する場合、単一メッセージ内で複数 Agent 呼び出しを並べる。
シナリオごとに別々の subagent を起動する（同一 subagent に複数シナリオを渡さない）。
理由: シナリオ間で実行者が前のシナリオの判断を学習してしまい、バイアスが入る。

## Red flag

- subagent に「A vs B」を直接評価させない（位置バイアスと self-preference バイアスでノイジー）
- 客観軸（精度、ステップ数、不明瞭点数、フェーズ弱点数）のみで比較する
- 質的比較が必要なら counterbalance（両順序を走らせ一致時のみ採用）
