# 失敗パターン台帳

イテレーション横断で、失敗モードを累積的に記録するリスト。
これが無いと、各イテレーションで同じクラスの誤りを何度も再発見することになり、
同じ `General Fix Rule` が表層の文言を変えて繰り返し表面化しているのに気付かないまま精度改善が停滞する。

## 運用ルール

1. 台帳は **対象プロンプト単位** で持つ。empirical-prompt-tuning 全体のグローバル台帳ではない
2. ワークフロー Step 5（差分適用）の **前** に台帳をスキャンする
3. 構造化振り返りの `General Fix Rule` が既存エントリと一致するなら、`Seen in` を更新
4. 一致した場合、新エントリを追加する前に「既存修正はなぜ再発を防げなかったか」を調査する
   - 文言の曖昧さ？
   - プロンプト内の位置が遅すぎ？
   - 例が欠けている？
5. 的を絞った修正にもかかわらず **3 回以上再発するパターン** は構造的シグナル
   → パッチを続けるのではなく「発散」基準にエスカレートする

## エントリ形式

```
- **Pattern 名**: 短く記述的なハンドル
  - Example: <あるイテレーションの代表的な Issue 文言>
  - General Fix Rule: <当該イテレーションの構造化振り返りから得たクラスレベルのルール>
  - Seen in: iter N, iter M, ...
```

## Pattern 名の命名指針

良い例: `skip 条項が無いときの過剰なテンプレ適用`
悪い例: `X が曖昧`

「何が」「どういう状況で」「どう失敗するか」を含めると、後で参照したときに即理解できる。

## 配置場所

対象プロンプトのリポジトリに `<対象パス>.ledger.md` 等で隣置きする方法と、
イテレーション記録の Output Format 内に台帳節を持つ方法のどちらかを選ぶ。
セッションを跨いで台帳を保ちたい場合は前者、単発のチューニングセッション内なら後者で十分。

## 例

```
- **skip 条項なしの過剰テンプレ適用**: 「~の場合は使わない」が無いと、subagent は適用範囲外でも skill を起動してしまう
  - Example: バグ修正タスクなのに refactoring skill を全面適用し、振る舞い変更まで含めた diff を出した
  - General Fix Rule: skill description に必ず「使わない場面」を 1-3 行で明記する
  - Seen in: iter 1 (refactoring), iter 3 (workflow-implement)

- **複数 critical の暗黙優先順位**: [critical] が複数並ぶと subagent が任意に優先順位を付ける
  - Example: 「[critical] 既存テストを壊さない」「[critical] カバレッジ 80% 以上」が並ぶと、後者を満たすためにテストを書き換えて前者を破った
  - General Fix Rule: [critical] が 2 つ以上あるときは「衝突した場合は X を優先」を明記する
  - Seen in: iter 2
```
